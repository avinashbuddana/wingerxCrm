## What exists

A self-contained, source-based WingerX-branded Whatomate distribution:
- Brand-first white SaaS visual language, custom WingerX *placeholder monogram*, navy text, blue interactions.
- Branded login, sidebar and mobile header; refinements to dashboard cards, chat bubbles, forms and page headers.
- Original Go WhatsApp Cloud API backend, PostgreSQL migrations, Redis queue, multi-tenant organizations, campaigns, team inbox, templates, chatbots and webhooks remain unchanged.
- Single Docker web service with built-in frontend and one worker.
- Separate Render Preview Blueprint with PostgreSQL and Redis, secrets generated by Render.

**Important:** This is NOT a GitHub fork yet. The connected GitHub app does not currently expose a fork/create-repository operation. The container build checks out a pinned upstream Whatomate commit, applies source modifications and compiles it. Your branded changes and launch configuration live in your own repository. To make an *official* GitHub fork, use https://github.com/shridarpatil/whatomate/fork and then port these files into that fork. Neither the original fork nor your existing CRM default branch has been modified.

## Build

\`\`\`bash
cd apps/wingerx-whatsapp-crm
docker build -t wingerx-whatsapp-crm .
\`\`\`

Docker requires external access to GitHub and npm/Go registries. Compilation requires substantial RAM/disk; the image is built with multi-stage Node 22 and Go 1.26.

## Deploy on Render

In Render, create a Blueprint from:
- **Repository:** \`https://github.com/avinashbuddana/wingerxCrm\`
- **Branch:** \`feat/wingerx-whatsapp-crm\`
- **Blueprint path:** \`apps/wingerx-whatsapp-crm/render.yaml\`

The Blueprint provisions a *separate* free web service, free PostgreSQL and free Key Value. It does not reuse Whatomate's prior test database. Initial user: \`admin@admin.com\`; retrieve its **generated** password in the service's **Environment** settings.

For test WhatsApp messages: Meta App → WhatsApp Cloud API → copy WABA ID, Phone Number ID and access token → WingerX WhatsApp CRM Settings → Accounts. Then configure Meta webhook to \`https://YOUR-RENDER-URL/api/webhook\` with the \`WHATOMATE_WHATSAPP__WEBHOOK_VERIFY_TOKEN\` secret. Subscribe to \`messages\`. Configure the Meta App Secret for signed webhook verification. Do not put access tokens, app secrets or customer phone lists in Git.

## Before connecting real customers

1. Upgrade database and Redis to persistent managed plans, and set up automated backups.
2. Switch media storage away from ephemeral \`/app/uploads\` to an S3-compatible implementation and verify compatibility.
3. Set a permanent admin password and keep \`WHATOMATE_APP__ENCRYPTION_KEY\` stable; losing it prevents decrypting stored tokens.
4. Configure Meta Embedded Signup App ID/Secret/Configuration ID if customers should connect with a Facebook button. Confirm Meta permissions and Business Verification requirements.
5. Validate tenant isolation, role permissions, audit logs, consent and marketing opt-out, campaign scheduling, queue retries and WhatsApp billing.
6. Set up domain \`wa.wingerx.com\` (or \`whatsapp.wingerx.com\`) only after HTTPS, webhooks, backup and acceptance testing.
7. WhatsApp voice calling / IVR require additional TURN/UDP infrastructure; this Render web service is intended for chat, campaigns and automation testing.
8. For client launch, review the source license; Whatomate is **AGPL-3.0**. Modified network-served software may require providing corresponding source to users. Keep attribution and license notices; seek legal review if business model requires it.
9. Replace \`wingerx-mark.svg\` with the approved WingerX logo artwork before public release. The current mark is an original placeholder, not the official logo.

## Architecture

\`WingerX WhatsApp CRM UI (Vue)\` → \`Whatomate API (Go)\` → \`PostgreSQL + Redis\` → \`Meta WhatsApp Cloud API\`

This remains a standalone WhatsApp CRM portal: the existing WingerX platform can link to it without merging the databases or disrupting the other CRM.

## CI / testing

Branding patches use fail-fast string checks to catch incompatible upstream UI changes. The code is committed but a successful Docker build and complete UI test run must be verified on Render before treating the portal as ready for customers.
